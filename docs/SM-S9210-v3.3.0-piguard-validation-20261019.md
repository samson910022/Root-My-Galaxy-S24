# SM-S9210 PI-guard exploit validation (2026-10-19)

## Result

One end-to-end Shizuku-mode install with the **PI-guard exploit rebuild**
succeeded on a physical SM-S9210 on 2026-10-19: bootstrap root was obtained on
`attempt=15/24`, KernelSU `late-load` completed, and the app's control-channel
check passed. This is the first recorded success with the PI-guard bytes; it
validates one run, not repeatability or the full post-install regression
suite. Evidence was collected with read-only checks after the run; the device
was not rebooted for this record.

## resetprop check (2026-10-19, later session)

A resetprop regression pass was run at about `03:35 +08:00` with the pinned
Phase-D `ksud` explicitly, to avoid the userspace drift described below. The
binary was pushed from the repository assets to
`/data/local/tmp/ksud-pinned` and verified as 4,995,304 bytes, SHA-256
`88748945…dc15049`, reporting `ksud 3.3.0 (uapi: 2)`.

| Operation | Result |
| --- | --- |
| Read `ro.build.fingerprint`, `ro.build.version.sdk` | rc=0, values returned |
| Set `debug.s24.check` `1` | rc=0; read back `1` via `resetprop` and via `getprop` |
| Delete `debug.s24.check` | rc=0; both reads then empty |
| Key props after the test | fingerprint unchanged, `ro.boot.verifiedbootstate=green`, `sys.boot_completed=1` |

No panic or property-service degradation followed: `su -c id` still returned
`context=u:r:ksu:s0`, `/proc/modules` still reported `kernelsu … Live`, and
SELinux stayed `Enforcing`. Only a non-persistent `debug.*` key was written; no
`persist.*` property was touched. The live Manager-bundled userspace also
passed a read check (`/data/adb/ksu/bin/resetprop ro.build.version.sdk` → 36).

### Userspace drift during this session

At `03:18`, opening the KernelSU Manager UI was followed by `/data/adb/ksud`
being replaced with the Manager APK `32601`'s bundled
`lib/arm64-v8a/libksud.so` (4,892,712 bytes, SHA-256
`99aaa607…3b5c41`, also reporting `3.3.0 (uapi: 2)`), overwriting the
Phase-D KDP loader that the app had staged there at `03:16`. The app keeps its
pinned build at `/data/local/tmp/ksud-s25u-kdp` (verified `88748945…dc15049`)
inside the app's `filesDir`, so the next install re-stages it. The replacement
mechanism (a Manager userspace refresh on launch) is inferred from the timing
and the digest match, not independently proven. This session also saw
transient `EACCES` on `/data/adb/ksud` while the Manager was deploying
`/data/adb/ksu/bin` and `lib/` (mtimes `03:32`); it cleared once deployment
finished.

## Validation scope

- Proven: one Shizuku app flow with the PI-guard exploit bytes obtained
  bootstrap root, loaded the bundled v3.3.0 KernelSU, passed the app's
  control-channel verification, and the Manager UI reports an LKM session as
  `已開始運作 [越獄模式]` with SELinux enforcing.
- Proven separately: the pinned `ksud` `resetprop` read/set/delete cycle works
  on this firmware without observable regressions.
- Proven previously: the overall install flow has succeeded on three separate
  dates (2026-10-03, 2026-10-07, 2026-10-19), and a reboot removes root because
  it is RAM-only; no persistence/auto-load mechanism exists. The PI-guard bytes
  themselves have one recorded success.
- Not established by this run: long-term stability or the temperature reached
  during the run.
- The reported panic-pattern concerns motivated the PI-guard rebuild; this
  single success does not by itself establish that the underlying problem is
  gone under repeated load.
- The support-feed e1q artifact remains unchanged; this note records the
  bundled candidate only.
